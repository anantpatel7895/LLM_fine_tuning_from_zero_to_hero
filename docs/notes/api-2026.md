# The 2026 API, and why every tutorial you find is wrong

**Read this before copying code from any blog post, YouTube video, or Stack Overflow answer.**

`transformers` went to **v5** and `trl` went to **v1**. Both were major releases with removals, not just deprecations. Essentially every fine-tuning tutorial written before 2026 uses API that no longer exists — and some of the changes are *silent*, meaning your code runs and does something different from what the tutorial intended.

This is not a footnote. For a beginner, "the tutorial is written against an API that was removed" is the single largest source of wasted evenings. Keep this file open.

## 1. `transformers` v5 — the renames and removals

| Old (what tutorials say) | Current v5 | Severity |
|---|---|---|
| `torch_dtype=torch.bfloat16` | **`dtype=torch.bfloat16`** | warns |
| default dtype was fp32 | **default is `dtype="auto"`** — loads in the checkpoint's saved precision | **silent numerical change** |
| `load_in_4bit=True` / `load_in_8bit=True` | **REMOVED.** Use `quantization_config=BitsAndBytesConfig(load_in_4bit=True, …)` | hard error |
| `Trainer(tokenizer=tok)` | **`Trainer(processing_class=tok)`** | hard error |
| `report_to` auto-detected wandb | **defaults to `"none"`** | **silent — your runs stop logging** |
| `use_cache` defaulted True | **defaults to `False`** in configs during training | benign, and correct |
| `trainer.train(model_path=…)` | `resume_from_checkpoint=` | hard error |
| `use_auth_token=` | `token=` | hard error |
| `no_cuda=` | `use_cpu=` | hard error |
| `per_gpu_train_batch_size` | `per_device_train_batch_size` | hard error |
| `config.rope_theta` | `config.rope_parameters['rope_theta']` | hard error |
| `tokenizer.encode_plus()` / `batch_decode()` | `tokenizer()` / `tokenizer.decode()` | hard error |
| `apply_chat_template()` returned `input_ids` | returns a **`BatchEncoding` dict** | **silent shape change** |
| `output_attentions=True` just worked | now **requires** `attn_implementation="eager"` | hard error |
| TensorFlow / Flax / JAX support | **REMOVED entirely** | ImportError |
| `transformers-cli` | `transformers` | hard error |
| `TRANSFORMERS_CACHE` | `HF_HOME` | silently ignored |
| pipelines `summarization` / `question-answering` / `translation` | **removed** — use `TextGenerationPipeline` | hard error |

**Removed with no deprecation period** (a tutorial passing any of these crashes): `overwrite_output_dir`, `logging_dir`, `past_index`, `tpu_num_cores`, `jit_mode_eval`, `_n_gpu`, `mp_parameters`, `ray_scope`.

**Minimum versions in v5:** Python ≥ 3.10, `huggingface_hub` ≥ 1.0, `accelerate` ≥ 1.1, `peft` ≥ 0.18, `bitsandbytes` ≥ 0.46.1.

> ⚠️ **Unverified:** the v5 release notes list `warmup_ratio` as removed. That is a *very* commonly copied argument and its removal would be surprising, so it may be a documentation error. **Test it empirically in Phase 04** and correct this file. `warmup_steps` survives and accepts a float, so that is the safe path meanwhile.

### The correct way to load a model for QLoRA in 2026

```python
from transformers import AutoModelForCausalLM, AutoTokenizer, BitsAndBytesConfig
import torch

bnb_config = BitsAndBytesConfig(
    load_in_4bit=True,
    bnb_4bit_quant_type="nf4",
    bnb_4bit_use_double_quant=True,
    bnb_4bit_compute_dtype=torch.bfloat16,   # A10 is bf16-native; never fp16 here
)

model = AutoModelForCausalLM.from_pretrained(
    "meta-llama/Llama-3.1-8B-Instruct",
    quantization_config=bnb_config,       # NOT load_in_4bit=True
    dtype=torch.bfloat16,                 # NOT torch_dtype=
    attn_implementation="sdpa",           # or "kernels-community/flash-attn2"
)
tokenizer = AutoTokenizer.from_pretrained("meta-llama/Llama-3.1-8B-Instruct")
```

## 2. `trl` v1 — `SFTTrainer` and `SFTConfig`

Current signature:

```python
SFTTrainer(
    model, args=None, data_collator=None, train_dataset=None, eval_dataset=None,
    processing_class=None,          # was: tokenizer=
    compute_loss_func=None, compute_metrics=None, callbacks=None,
    optimizers=(None, None), optimizer_cls_and_kwargs=None,
    preprocess_logits_for_metrics=None,
    quantization_config=None,       # NEW: pass BitsAndBytesConfig straight in
    peft_config=None, formatting_func=None,
)
```

| Old | Current |
|---|---|
| `tokenizer=` | **`processing_class=`** |
| `max_seq_length=2048` | **`max_length`**, and note the default is only **1024** |
| `dataset_text_field=` on the trainer | now on **`SFTConfig`** (default `"text"`) |
| `DataCollatorForCompletionOnlyLM(response_template=…)` | **REMOVED.** See §3 |
| `packing=True` meant naive concatenation | see §4 — the default strategy changed and this matters |
| `truncation_mode="keep_end"` | deprecated; only `"keep_start"` |
| `pad_token=` in the config | deprecated — set `tokenizer.pad_token` and pass via `processing_class` |

### `SFTConfig` defaults that differ from plain `TrainingArguments`

A tutorial that sets these explicitly is often *fighting* the new defaults rather than helping:

| Setting | `SFTConfig` default | Plain `TrainingArguments` |
|---|---|---|
| `gradient_checkpointing` | **`True`** | `False` |
| `bf16` | **`True`** (if `fp16` unset) | `False` |
| `learning_rate` | **`2e-5`** | `5e-5` |
| `logging_steps` | **`10`** | `500` |
| `optim` | `"adamw_torch_fused"` | `"adamw_torch"` |
| `loss_type` | **`"chunked_nll"`** | n/a |
| `use_cache` | `False` | n/a |
| `report_to` | `"none"` | `"none"` |

⚠️ **`learning_rate=2e-5` is the full-fine-tuning value, not the LoRA value.** For PEFT you want roughly **1e-4** — TRL's own docs say so explicitly. Accepting the default for a LoRA run is a quiet way to undertrain.

⚠️ **`loss_type="chunked_nll"`** is the chunked cross-entropy that avoids materializing the full logits tensor. It is **incompatible with `use_liger_kernel=True`**, which forces `"nll"`. See [NUMBERS.md §3](../../NUMBERS.md) — on Llama-3.1-8B at sequence length 4096, that is 1.47 GiB chunked versus 4.89 GiB naive. Do not turn it off casually.

New in v1 and worth knowing: `activation_offloading`, `chat_template_path`, `router_aux_loss_coef` (MoE), `parallelism_config` (accelerate N-D parallelism), and `loss_type="dft"` (Dynamic Fine-Tuning).

## 3. Completion-only loss — the mechanism changed entirely

This is the most important change for Phase 03, because it is the area where beginners most often get silently wrong behaviour.

**`DataCollatorForCompletionOnlyLM` has been removed.** Every tutorial that uses `response_template="### Assistant:"` is describing machinery that no longer exists.

The replacements:

| Your data shape | What to do |
|---|---|
| **Prompt-completion** — `{"prompt": …, "completion": …}` | Nothing. **`completion_only_loss` is `True` by default** for this format |
| **Conversational** — `{"messages": [...]}` | Set **`assistant_only_loss=True`** |

⚠️ **`assistant_only_loss=True` requires the chat template to contain `{% generation %}` / `{% endgeneration %}` markers** around the assistant content. TRL auto-patches some known families (Qwen3 among them), but for other models it will **silently fail to mask what you expect**.

This is precisely why Phase 02's deliverable is *a chat template you wrote yourself, in version control, with tests* — and why Phase 03 builds `mask_inspector.py`. **Verify per model. Do not trust the flag.**

## 4. Packing — the cross-contamination problem is fixed by default

Older material warns that `packing=True` lets one packed example attend to another, contaminating the batch. **That warning describes the old behaviour.**

| Strategy | Behaviour |
|---|---|
| `packing_strategy="bfd"` | **The current default.** Best-fit-decreasing bin packing, and it **auto-enables `padding_free`**, so packed sequences do **not** attend across boundaries |
| `packing_strategy="wrapped"` | The old aggressive behaviour — concatenate and cut mid-sequence. This is the one the warnings were about |
| `packing_strategy="bfd_split"` | Renamed from `"bfd-requeue"` |

So: `packing=True` in 2026 is safe and is what you want. **But understand the mechanism anyway** (Phase 10) — "how does packing avoid cross-attention between examples?" is a common interview question, and the answer is `position_ids` plus variable-length attention, not magic.

## 5. `trl` v1 — `DPOTrainer` and `DPOConfig`

| Old | Current |
|---|---|
| `max_prompt_length`, `max_completion_length` | **GONE.** Only `max_length` (default 1024) |
| `loss_type="sigmoid"` (a string) | **`loss_type: list[str] = ["sigmoid"]`** — now a *list*, with `loss_weights` for multi-objective (MPO) |
| `tokenizer=` | `processing_class=`, and **padding side must be `"left"`** |
| — | `quantization_config=` for QLoRA-DPO |
| `padding_free=True` | ⚠️ **temporarily unavailable** since the DPO refactor — setting it warns and falls back to standard padding |

`learning_rate` default is **1e-6**; the docs suggest ~1e-5 for adapters. `beta` default 0.1.

### The reference-model memory win, which matters enormously on 24 GB

- `ref_model=None` → the trainer uses the initial policy automatically.
- **With PEFT, no separate reference model is materialized at all.** The trainer disables the adapters to compute reference log-probs. This is the single biggest memory saving available for DPO on your hardware — a naive DPO setup would need two copies of an 8B.
- `precompute_ref_log_probs=True` removes the reference model from memory entirely, at the cost of a preprocessing pass.

New loss types since the older tutorials: `sigmoid_norm` (SimPO), `discopop`, `apo_zero` / `apo_down`, `aot`, `sft`, plus `ld_alpha` (LD-DPO) and `f_divergence_type`.

## 6. Attention on A10 (sm_86) — and stop compiling flash-attn

| Backend | On A10? | Note |
|---|:---:|---|
| `sdpa` | ✅ **default, and a good one** | PyTorch's own flash kernel. Does not materialize the `s × s` matrix |
| `flash_attention_2` | ✅ | Buys roughly **10–20% over sdpa on Ampere** — not the 3× the marketing implies |
| `flash_attention_3` | ❌ | **Actively disabled on compute capability 8.6** — not enough shared memory for the implementation. This is stronger than "Hopper-optimized"; it will not run |
| FlashAttention-4 | ❌ | Blackwell (SM100+). Irrelevant here |
| `flex_attention` | ✅ | Useful for custom masks |
| `eager` | ✅ | Required if you want `output_attentions=True` |

**The modern way to get FA2 — no compilation:**

```python
model = AutoModelForCausalLM.from_pretrained(
    "...", attn_implementation="kernels-community/flash-attn2")
```

The `kernels` library downloads a prebuilt kernel from the Hub at runtime. This replaces the traditional 30-minute `MAX_JOBS=4 pip install flash-attn --no-build-isolation` ritual that frequently OOMs during compilation. You can also switch at runtime: `model.set_attn_implementation("sdpa")`.

> ⚠️ **Verify in Phase 00:** the Hub kernel variants are keyed on torch and CUDA version, not GPU architecture, so it could not be confirmed from the variant names that sm_86 SASS is included. FA2 supports Ampere so it very likely is — but check on the box, and keep `pip install flash-attn==2.8.3.post1` documented as the fallback.

## 7. FSDP2 vs DeepSpeed — and the precision table that decides it for a 2-GPU box

**Default choice: FSDP2 (built into torch), via `accelerate`.** Reach for DeepSpeed only for the one case below.

The deciding fact, from HuggingFace's own concept guide:

| Framework | Load dtype | Mixed precision | Prepared params | Optimizer states |
|---|---|---|---|---|
| FSDP | bf16 | **none** | **bf16** | **bf16** |
| FSDP | bf16 | bf16 | fp32 | fp32 |
| DeepSpeed | bf16 | bf16 | **always fp32** | **always fp32** |

**DeepSpeed always upcasts to fp32.** On a 64-GPU cluster that overhead amortizes; on your **2 GPUs it does not.** FSDP can run pure-bf16 end to end, which is the difference between 12 and 6 bytes per trainable parameter — see [NUMBERS.md §6](../../NUMBERS.md).

So, for this box:

| Job | Use |
|---|---|
| All LoRA / QLoRA work | **plain DDP.** Communication is ~8 ms/step. Do not reach for FSDP |
| Full fine-tune of 1.7B / 3B / 4B | **FSDP2**, pure-bf16 mode |
| Full fine-tune of 8B (the "here is the wall" demo) | **DeepSpeed ZeRO-3 + CPU optimizer offload** — see below |

**Why the 8B case is DeepSpeed-only:** it needs CPU offload of the *optimizer states only*, keeping parameters on the GPU. FSDP2's `cpu_offload=true` is **all-or-nothing** — it drags parameters off too. DeepSpeed can offload optimizer-only, and to NVMe as well. That configuration (~17.3 GiB/rank + ~15 GiB of CPU RAM with an 8-bit optimizer) is the only one that fits.

**Current FSDP2 config shape:**

```json
{ "version": 2,
  "reshard_after_forward": true,
  "cpu_offload": false,
  "auto_wrap_policy": "TRANSFORMER_BASED_WRAP",
  "transformer_layer_cls_to_wrap": ["LlamaDecoderLayer"],
  "state_dict_type": "FULL_STATE_DICT",
  "cpu_ram_efficient_loading": true,
  "activation_checkpointing": true }
```

> ⚠️ **A real trap.** FSDP2's `activation_checkpointing` and `TrainingArguments.gradient_checkpointing` **cannot both be set — it raises an error.** And `SFTConfig` defaults `gradient_checkpointing=True`. So a naive FSDP2 + `SFTConfig` combination crashes. Set exactly one. *(Inferred from two separate docs — confirm empirically in Phase 10 and correct this note.)*

`reshard_after_forward=false` trades memory for one fewer all-gather, which is a good trade on PCIe if you have the headroom. `state_dict_type` defaults to `FULL_STATE_DICT`; sharded checkpoints only reload into FSDP, so always save a FULL one at the end.

**Vocabulary mapping**, because two names for one thing causes real confusion:

| FSDP | DeepSpeed |
|---|---|
| `NO_SHARD` | DDP / ZeRO-0 |
| `SHARD_GRAD_OP` | ZeRO-2 |
| `FULL_SHARD` | ZeRO-3 |
| `HYBRID_SHARD` | ZeRO++ Stage 3 |

(Sharding-strategy enums are an FSDP**1** concept; FSDP2 expresses the same thing with `reshard_after_forward`.)

**No-NVLink guidance:** minimize collective volume. Prefer ZeRO-2 / `SHARD_GRAD_OP` over ZeRO-3 when it fits (no parameter all-gathers), set `reshard_after_forward=false`, raise `gradient_accumulation_steps` to amortize the fixed per-step communication cost, and enable `fsdp_backward_prefetch: BACKWARD_PRE`.

## 8. Unsloth — and why the 2-GPU story is not built on it

- Current version 2026.9.2, very actively developed, genuinely ~2× faster with up to 70% less VRAM on a single GPU.
- **Multi-GPU support is still not officially released.** The docs say they are "working hard to make multi-GPU support much simpler" and will announce it "soon." What exists today works via `accelerate launch` / `torchrun` and is described as "complex and requires manual setup."
- ⚠️ **Requires torch ≥ 2.4, < 2.12** — so it is **incompatible with torch 2.14.** Adopting Unsloth means pinning an older torch than the rest of the stack.

**Therefore:** Phase 17 treats Unsloth as the single-GPU speed and memory chapter, which is its genuine strength. Nothing multi-GPU in this curriculum depends on it.

For the config-driven frameworks: **Axolotl 0.18.0** has mature FSDP1/FSDP2/DeepSpeed and composable CP+TP+FSDP, and is the better pick for multi-GPU. **LlamaFactory 0.9.5** (note: the repo was renamed from `LLaMA-Factory`) explicitly advertises *"FSDP+QLoRA that fine-tunes a 70B model on 2×24 GB GPUs"* — which is exactly your hardware, and makes a genuinely impressive optional capstone. *(That technique dates to 2024; it was not verified against the transformers-v5 / trl-v1 stack. Test before relying on it.)*

## 9. Data tooling — two well-known projects are effectively dead

⚠️ **`distilabel` and Argilla are not maintained.** Almost every 2024–2025 article on synthetic data generation recommends them.

- **`distilabel`**: last real code commit **January 2025**; last release 1.5.3, same date. Its README states plainly that *"the original authors have moved on to other projects"* and that community members are "working towards the next release." As of now, 19 months with no release. The related DataCraft UI was discontinued in July 2025.
- **`argilla`**: last release 2.8.0, March 2025; last real code commit the same month.

The datasets they produced remain perfectly good and are still widely downloaded. But a 2026 curriculum that says "use distilabel" points you at abandoned software.

**What this repo uses instead:**

| Need | Tool |
|---|---|
| Dedup, quality filtering, decontamination | **`datatrove`** 0.10.0 — HuggingFace's own FineWeb pipeline, actively maintained |
| MinHash-LSH primitive (to derive `(b, r)` yourself) | `datasketch` 2.0.0 |
| Semantic / embedding dedup | `semhash` 0.4.1 |
| Synthetic generation | **roll your own on a local vLLM server** — about 100 lines, no abandonment risk, and honestly the most common 2026 practice. `NeMo Curator` 1.3.0 is the maintained batteries-included alternative |
| Verifiable-reward environments (Phase 15) | `verifiers` 0.3.1 — very actively developed |
| Data mixing | No dominant library. Axolotl and LlamaFactory both express mixtures as per-dataset sampling weights in YAML — that is the pragmatic pattern to copy |
| Annotation UI | ⚠️ **genuine gap.** No maintained OSS successor to Argilla was found |

## 10. Evaluation tooling

| Tool | Status | Use it for |
|---|---|---|
| **`lm-eval`** 0.4.13 | ✅ very active | Public benchmarks. The default. **Use the vLLM backend — 10×+ faster** and it fits an A10 |
| **`inspect-ai`** 0.3.263 | ✅ extremely active (UK AISI) | ⭐ Custom, agentic and LLM-as-judge evals. Good solver/scorer abstractions |
| `deepeval` 4.2.2 | ✅ extremely active | Pytest-style assertions and thresholds; good for CI-style regression gates. Vendor-adjacent, so read its docs with that in mind |
| `lighteval` 0.13.0 | ⚠️ main branch active but **no release since Nov 2025**, 400+ open issues | Usable, but do not build the curriculum's backbone on it |
| `crfm-helm` 0.5.16 | maintained | Context for how leaderboards work. Overkill for evaluating your own fine-tunes |
| `math-verify` 0.9.0 | — | Deterministic grading of reasoning outputs |

**Three judge caveats worth remembering:** prefer **pairwise A/B over absolute 1–5 scoring** when comparing fine-tunes; **randomize response order** to counter position bias; and **never judge with the same model family you fine-tuned** — self-preference bias is real and measurable.

## 11. Model-family cautions

⚠️ **Some current small models are multimodal architectures and will not behave like plain text models.**

| Model | Architecture | Caution |
|---|---|---|
| `Qwen/Qwen3.5-2B`, `Qwen3.5-4B` | `Qwen3_5ForConditionalGeneration` | **Multimodal.** TRL may route them through a vision-language collator; `max_length` truncation can destroy image tokens |
| `google/gemma-4-e4b` | `Gemma4ForConditionalGeneration` | **Multimodal, and ~8.0 B stored parameters despite the "E4B" name.** Budget it as an 8B for memory, not a 4B |

**For a text fine-tuning curriculum, prefer pure `ForCausalLM` models:** `Qwen/Qwen3-1.7B`, `Qwen/Qwen3-0.6B`, `Qwen/Qwen3-4B`, `HuggingFaceTB/SmolLM3-3B`, `meta-llama/Llama-3.2-1B` / `3B`, `meta-llama/Llama-3.1-8B-Instruct`, `mistralai/Mistral-7B-v0.3`.

⭐ **`HuggingFaceTB/SmolLM3-3B` is the best teaching model in the 3B class** — Apache-2.0, and its *entire training recipe is published*, so you can compare your choices against a fully open reference.
